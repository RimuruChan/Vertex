# Vertex OJ — 赛制与榜单设计

Vertex 支持五种计分模式:**ICPC**、**IOI**、**传统 OI**、**乐多**和 **CF 积分**。本页说明各自的计分模型、封榜语义、
裁判权限、重测与答疑,以及为什么这些机制在改判后依然正确。

## 1. 赛制与预设

|                    | ICPC                          | IOI              | OI                     |
| ------------------ | ----------------------------- | ---------------- | ---------------------- |
| 排名主键           | 通过题数                      | 总分             | 总分                   |
| 次要键             | 罚时(小者优先)                | 达到该分数的时间 | 达到该分数的时间       |
| 单题计分           | 首次 AC 之前的失败各罚 N 分钟 | **历史最高分**   | **最后一次提交的分数** |
| 首次 AC 之后的提交 | 完全忽略                      | 不会降低已得分   | 会覆盖(最后一次为准)   |
| 罚时               | 有                            | 无               | 无                     |
| 默认反馈           | 仅最终判定                    | 完整（平台模式） | 不反馈                 |

`contests.rule` 取 `icpc` / `ioi` / `oi` / `leduo` / `cf`，默认值为 `icpc`。
项目尚未上线，赛制与反馈约束直接并入 `000001_init`，不保留增量迁移。OI 的赛中无反馈策略由比赛应用层统一执行。

创建比赛和比赛设置页均提供五个预设，切换会更新计分、反馈、编译错误计数和提交可见性；名称、时间、封榜计划、题目及报名设置保持不变。OI 的反馈固定为 `none`，不允许开启实时正式结果；封榜计划在 OI 中不生效，赛后直接公开最终榜单。其他赛制的反馈仍可单独调整。

### ICPC 罚时

```text
penalty = (首次 AC 距离开赛的秒数) + (首次 AC 之前的失败次数 × penalty_minutes × 60)
```

- 未通过的题**不贡献罚时**,只记录尝试次数。
- `penalty_minutes` 每场可配,默认 20(ICPC 官方规则)。
- `penalize_compile_error` 决定编译错误是否算作一次失败尝试；ICPC 预设不计入。关掉后编译错误连尝试次数都不计。

### IOI 与 OI 的区别

两者都按总分排名，区别包括**哪一次提交算数**和**赛中反馈**：

- **IOI**:取该题历史最高分。选手能看到反馈,可以不断改进,后交的差解不会伤害成绩。
- **OI**:取最后一次提交的分数。选手看不到反馈,因此「保留更早的好成绩」不是他们能做的决策;
  最后一次提交为准是 NOIP/CSP 的实际规则。

OI 的最后一次编译错误同样覆盖之前成绩并记零分；排队、评测中和系统错误不构成有效评测结果。

### 乐多

每次有效提交先换算到题目分值，再计算 `floor(分值 × max(0.7, 0.95^(次数−1)))`，最终取历次折算后的最高分。编译错误计入次数并记零分；系统错误、排队和评测中的提交不计入。得到原始满分即视为通过，实际积分仍可能因为折扣低于题目满分。

### CF 积分（不含 Hack／预测试）

本项目直接对完整测试数据评测；只有 AC 才有积分，取第一次 AC 及其之前的错误提交。后续提交不影响该题得分。设题目基准分为 `P`，比赛时长为 `D` 分钟，首次 AC 时间为开赛后 `t` 分钟，之前非编译错误的失败次数为 `w`：

```text
score = max(floor(0.3 × P), P - floor(120 × P × t / (250 × D)) - 50 × w)
```

`t`、`D` 向下取整，`D` 至少为 1。无 AC 得零分。编译错误不扣分。本模式没有预测试、锁题、Hack 得分或首测试点失败豁免；每个非 CE 的失败正式评测都计入 `w`。因此这是明确限定的 CF 积分模式，不宣称复现 Codeforces 的完整比赛流程。建议题目基准分采用 500、1000、1500 等，并在题目编排中设置。

乐多和 CF 均按总分排名，同分共享名次；同分行按最后通过时间、用户名稳定排序。计分与公开封榜投影由同一算法计算，重测后重新推导。

判题给出的是 0-100 分,按题目的 `points` 缩放,**向零取整**——部分分永远不会被放大成满分。
满分才算「通过」,这样 IOI/OI 榜单上的通过数与首杀高亮仍然有意义。

## 2. 计分是纯函数

计分逻辑写成不依赖数据库的纯函数(`internal/modules/contest/scoring.go`):

```go
func ScoreCell(rules ScoringRules, submissions []ScoredSubmission) Cell
```

判题完成后,`RebuildCell` 读出该 (比赛, 用户, 题目) 的**全部提交**,交给 `ScoreCell`
重算,再整体写回积分格。这样做的代价是每次判完多一次小范围查询,换来的是:

- **改判安全**:重测、改判、删除提交都会收敛到同一结果,不存在「加错一次罚时」这种
  只能靠重建数据库修复的偏差。
- **可测试**:罚时、封榜切分、IOI/OI 取分规则全部有单元测试,不需要起数据库。
- **配置可改**:改了 `penalty_minutes` 或题目分值,`Update`/`SetProblems` 会在同一事务里
  重算整场榜单。

同一格的并发重算用 `pg_advisory_xact_lock` 串行化。

## 3. 封榜:一行两套视图

积分格同时保存两套数值:

| 列                                                 | 含义                                       |
| -------------------------------------------------- | ------------------------------------------ |
| `attempts` / `penalty_sec` / `score` / `solved_at` | **裁判视图**:包含封榜后提交的完整真相      |
| `public_*`                                         | **封榜视图**:只统计 `freeze_at` 之前的提交 |
| `pending_count`                                    | 封榜后的提交数,榜单渲染为 `?`              |

两套值在同一次 `ScoreCell` 里算出。榜单读取因此是**两条查询**(参赛者 + 积分格),
与参赛人数无关;旧实现要为每个用户单独查一次提交,几百人的比赛会退化成几百次查询。

- `freeze_at` 为空 = 不封榜,两套视图相同。
- `unfreeze_at` 到点自动解榜;为空则一直封到手动切换。
- 解榜后普通查看者也读取完整积分格、总分与首杀，`juryView` 仍为 false。完整结果投影与裁判身份是两件事，不能用同一个开关决定；封榜待定数只在封榜投影中返回。
- 待定格及选手待定标记使用蓝色。ICPC、CF、IOI、乐多在封榜前已经通过且成绩不再受后续提交影响时，公开格不再叠加待定标记。判断只依据封榜前的结果；封榜后才通过仍显示待定。底层保留提交计数，重测撤销封榜前的通过后会重新显示待定。
- 开赛前普通用户不能通过榜单的题目元信息提前看到赛题，赛务可按权限预览。
- **裁判和观察员可以请求未封榜的榜单**，普通选手无论怎么传参数都拿不到——
  服务端决定给哪一套值,DTO 只序列化被授权的那一套。

## 4. 裁判权限

| 角色                            | 比赛设置/编排 | 未封榜榜单 | 全部提交 | 答疑回复 | 授权/转让 |
| ------------------------------- | :-----------: | :--------: | :------: | :------: | :-------: |
| owner、域资源管理者、站点管理员 |       ✓       |     ✓      |    ✓     |    ✓     |     ✓     |
| 编辑协作者 `editor`             |    开赛前     |            |          |          |           |
| 比赛裁判 `jury`                 |               |     ✓      |    ✓     |    ✓     |           |
| 观察员 `observer`               |               |     ✓      |    ✓     |          |           |
| 选手                            |               |   按封榜   |  仅自己  |  仅提问  |           |

`contests.owner_id` 与 `created_by` 分开；owner 转让不会改变创建记录或公开编号。`contest_access` 支持同域用户/group 的 editor、jury、observer、participant 多个独立授权。`contest_staff` 现在是只读有效赛务视图，包含 group 继承，只在账号和域成员均有效时生效。编辑协作者可提前预览赛题，但开赛后不能通过修改结束时间/反馈/编排来绕过赛务数据权限。

`admission=members` 面向有效域成员，`restricted` 要求 participant 授权；参赛资格不自动建立报名记录。报名事务复核当前权限、报名策略、时间和已验证的密码 hash。观察员/编辑协作者不能提交；未报名的 owner/裁判可以在比赛时段发非参赛测试提交，已有选手报名记录者转为赛务后不能继续提交，避免测试提交进入其旧榜单行。

### 报名策略

比赛详情 → 设置 → 报名设置提供两个独立配置：

| 字段 | 默认 | 作用 |
| --- | --- | --- |
| `allowSelfRegistration` | `true` | 符合资格的用户可自行报名；关闭只暂停新增报名，不取消已有记录 |
| `allowLateRegistration` | `false` | 开启后允许从开赛时刻起到结束前继续报名；关闭时在开赛时刻截止 |

比赛结束时及之后始终不接受新报名。关闭自助报名时，赛中报名选项不生效但保留配置；迟到报名不延长比赛时间，计分仍以统一开赛时间为基准。已报名用户的重复请求幂等，不产生第二条记录；成员失效、参赛资格撤销和赛务角色限制仍按原规则生效。

只有 owner / 域资源管理者可改报名策略，编辑协作者和普通裁判不获得此能力。密码赛、域成员、participant 用户/group 授权都不会被这两个开关绕过。`permissions.register` 反映当前策略与时间窗口，报名写入在比赛行锁内再次复核，防止等待期间的关闭被绕过。关闭自助报名不等于自动代报名，participant 授权仍只是资格。

API 创建请求省略字段时采用上述默认值；更新请求省略字段时保留锁内读取的当前值，显式 `false` 正常保存。开发期 init schema 增加对应两列；已有数据库不会自动升级，应使用新初始化的开发/测试库，不能将删除旧数据当作普通更新步骤。

赛务读取、报名、答疑、比赛提交、协作管理及比赛裁判重测已按当前权限接入。重测控制台由 `viewJury` / `rejudge` 驱动：观察员可看记录和改判详情，只有具备重测能力的用户才能发起或取消。完整多域界面及跨资源最终验收仍见实施计划，不能据此宣称整体重设计完成。

### 比赛详情工作流

`/d/{domain}/manage/contests` 只负责查找、创建和进入。标题/编号搜索在数据库中先按域与当前协作权限过滤，再分页并计数；公开列表与协作列表分别授权。创建默认私有，随后进入 `/d/{domain}/contests/{number}?tab=settings`，不在列表弹窗里继续编辑。

同一详情的「设置」「题目编排」「协作权限」按 capabilities 展示。设置与编排分别保存，切换分区及保存另一分区不覆盖未保存草稿；URL 记录当前分区，切换资源或账号则重新授权。编辑协作者在开赛前可准备比赛，不能修改可见性、密码、参赛资格或报名策略；开赛后设置与编排只读。观察员可审阅，但没有保存和删除入口。

题目选择从本域有权读取的题目中分页搜索，未发布题目不能加入。编排提交明确的 `problemId/label/color/points`；排序保留题号、分值、颜色及固定的发布版本。新增题目默认 A…Z、AA…；自定义题号以字母开头，最多 8 位字母或数字，不能重复，避免与数字题目编号及 URL 分隔符混淆。

密码赛留空密码表示在事务锁内保留当前哈希，不重新写回读取时的旧值；只有明确输入新密码才轮换。删除入口位于详情，后端拒绝删除已有报名、提交、澄清或重测记录的比赛；无活动记录的比赛可删除，原题目不受影响。该检查与资源锁、域锁一起执行，避免级联删除参赛历史。

## 5. 比赛中的反馈控制

`contests.feedback` 决定选手在**比赛进行中**能看到多少:

| 取值      | 选手看到                    |
| --------- | --------------------------- |
| `full`    | 判定 + 逐测试点 + 用时内存  |
| `summary` | 只有最终判定                |
| `first_error` | 最终判定、首个失败点编号和类型；CE 保留编译诊断，不返回测试点资源用量或检查器输出 |
| `none`    | 只有「已提交」(`Submitted`) |

- 比赛结束后一律恢复完整反馈。
- 裁判、观察员和管理员不受限制。
- **无论哪一档,选手都能看到自己提交存在、以及提交的源码**——隐藏这些只会让人以为提交丢了。
- 排队中的提交仍然显示 `Pending`/`Judging`,同样是为了让选手知道提交没丢。
- 列表的 `status` 过滤也使用脱敏后的状态，防止用查询总数探测隐藏判定；禁反馈终态可用 `Submitted` 查询。

屏蔽在服务层完成(`submission.Redact`),列表接口按比赛缓存一次判定级别,
一页提交只查一次比赛配置。

## 6. 重测(Rejudging)

单条重测与批量重测走同一条内部路径 `requeueSubmission`:取消未完成的 job、
`judge_generation + 1`、清空旧结果、插入新 job、重算积分格。

批量重测是一个**批次**(`rejudgings`),按选择器展开:

```text
contestId / problemId / userId / language / status / submissionIds  (AND 组合)
```

选择器**不能为空**:无限制的重测会把整个站点的提交全部重判,这不是可以「手滑」的操作。

比赛裁判的选择器必须固定其有权限的比赛；题目 owner 的题目级重测仅覆盖 `contest_id IS NULL` 的练习提交。批次的读取、变更和取消继续验证其父资源权限，撤权后不能凭已知批次 UUID 继续操作。

重测 generation 操作在域内以独立事务 advisory lock 串行化；这不是队列领取锁，Worker 不依赖它。批量重测先锁相关 job，再锁 submission，与 Worker 的提交顺序一致。授权稳定性使用域共享锁和资源授权共享 guard，不提前占用 Worker 要更新的统计行；角色/owner/协作变更持有对应排他 guard。创建、单条重测和取消在同一事务记录审计事件。
单批上限 5000 条。

每个成员记录展开时分配到的 `generation`,这是围栏:

- **进度**由 `submissions` 当前状态推导,worker 不需要上报任何东西;
- 成员的 generation 已经前进,说明它被更晚的重测接管,本批次不再对它负责;
- **取消**会撤回尚未开始的 job，并原子恢复这些提交在重测前的完整判定快照；已经领取或判完的结果继续保留;
- `changed` 统计判定或分数与重测前不同的条数,这是裁判真正关心的数字。

> 与 DOMjudge 的差别:DOMjudge 的重测是两阶段的(先产生新 judging,裁判确认后 apply)。
> Vertex 是**立即生效**的:新结果直接写回提交并重算榜单,再通过「改判详情」让裁判复核。
> 这与 Vertex 既有的 generation 围栏模型一致,代价是无法在应用前预览。

## 7. 答疑(Clarifications)

选手提问、裁判回答与全场公告共用一张表:

- `parent_id` 为空 = 新话题;裁判的回复挂在话题下,并把话题标记为已回答。

答疑读取与写入按当前域和比赛权限 fail-closed：赛务可以读取，其他用户须满足比赛访问和报名条件；公开赛允许已登录用户读取其可见话题。仅知道 UUID 或曾创建比赛不授予赛务权限。转让、停用和撤销授权后重新按当前资源权限判断。

- 裁判回复**默认只发给提问者**(继承话题作者),不会因为忘记填收件人就变成全场广播。
- `from_jury` 且无收件人 = 全场公告,所有选手可见。
- 选手只能读到:自己的话题、发给自己的回复、全场公告。这条过滤在 SQL 里做,
  大型比赛不会把所有队伍的提问发给每个客户端。
- 提问窗口 = 比赛开始到结束;赛前无题可问,赛后通道关闭。

## 8. 前端渲染

榜单组件按赛制切换列:

- **ICPC**:`通过` + `罚时` 两列,格内显示解题分钟数或 `−失败次数`。
- **IOI/OI/乐多/CF 积分**:`总分` 一列,格内显示该题得分,表头显示满分或基准分。
- 首杀用琥珀色高亮并加奖杯图标;封榜期间的提交显示 `+N?`。
- 题目列显示 `label`(A/B/C)与气球颜色 `color`。

前端只渲染服务端给的数字,**封榜数据不会经由客户端泄漏**。

## 10. 已知边界

- **子任务计分**:题目包里的测试点分组与分值已写入 `problem_testdata.config_json`,
  但判题侧仍按「首个非 AC 即最终判定」聚合,IOI 的部分分目前来自判题给出的整体
  score,不是按子任务累加。
- **气球分发**:记录了颜色,但没有气球队列/确认流程。
- **实时推送**:榜单与答疑均为轮询(榜单 5s、答疑 15s),尚未使用 WebSocket。
- **奖牌与打印**:未实现。

### 反馈预设与正式赛事规则的区别

ICPC 默认 `summary`；CF 积分默认 `first_error`；OI 固定 `none`。反馈枚举约束已包含在 `000001_init` 中。已有比赛不会因为预设默认值变化而自动改写，需要重新应用预设并保存。

IOI 2024 官方规则按子任务报告得分，并对每个未满分子任务反馈最低分测试点中的首个编号和结果，不公开实际测试数据、选手输出或其他执行细节。当前平台尚无对应的子任务反馈投影，IOI 预设的 `full` 是逐点反馈模式，不能视为官方粒度的复刻。参见 [IOI 官方规则](https://www.ioi2024.org/contest-rules)。

洛谷关于乐多的官方说明只规定赛中能查看评测结果，没有明确逐测试点反馈范围。这里保留可调整的 `full` 预设，这是平台选择，不宣称它是赛制强制要求。参见 [洛谷比赛说明](https://help.luogu.com.cn/manual/luogu/contest)。
